# V40.1 privacy changes and release steps

## What changed

- The report public-location checkbox starts unchecked. With `Exact` selected and explicit consent, exact GPS is included in the report for signed-in users. Without consent, the report stores no location.
- `Approximate`: when the user opts in, only the selected district label is shared; the map uses its representative point and does not ask for GPS.
- With `Off` selected, public-location sharing is disabled. Users can leave the checkbox off and describe the place in text.
- V40 report reads require an explicit privacy classification. This keeps older, unclassified records out of the normal signed-in feed until they are migrated.
- User profile writes are restricted to known application fields. Phone-verification flags must agree with the Firebase Authentication phone claim.
- Privacy policy text now describes phone, push token, image, report and location handling.

## Before publishing

1. Keep V39 as the rollback copy. Test V40.1 on a staging Firebase Hosting channel/project first.
2. Review Firebase Console > Firestore > Rules, then deploy the V40.1 `firestore.rules` from this app folder: `firebase deploy --only firestore:rules,firestore:indexes --project lankaalert-2ee5c`.
3. Check sign-in, profile edits (including age, emergency contacts and photo), phone verification, push notifications, Family Circle, report likes and all three location modes. User profile changes use a field allowlist; add a field to the rules only when the app genuinely needs it.
4. Migrate legacy reports before release so they return to the feed without exposing exact GPS. Back up/export Firestore first. From `backend-blaze-only/functions`, install the declared dependencies (`npm install`) and run `node migrate-report-privacy.js` with Firebase Admin Application Default Credentials for project `lankaalert-2ee5c` (for example, a service account JSON referenced by `GOOGLE_APPLICATION_CREDENTIALS`, or `gcloud auth application-default login`). The script moves the old exact location into the restricted `reportLocations` collection, then removes location fields from legacy public reports because those users never gave the new per-report consent. Reports without usable coordinates are marked `off`. Review the counts and a few documents in Firestore before proceeding.
5. Publish hosting after the migration: `firebase deploy --only hosting --project lankaalert-2ee5c`. Deploy Functions only if their code changes; V40.1 has not changed the scheduled Functions.
6. Verify while signed in as an ordinary test account that a new report shows exact coordinates only when its public-location checkbox was selected and that old reports show no location unless the user submits a new report and opts in. Also test Approximate and Off reports.

## Manual items that still matter

- Configure and enforce Firebase App Check for Firestore and other Firebase services in the Firebase Console after testing; the browser app currently does not initialize App Check.
- Inspect the deployed Cloudflare R2 upload Worker. Its source/configuration is not in this copy, so verify authenticated uploads, file type/size limits, public read policy and deletion/retention there. V40.1 converts report photos to resized JPEGs in the browser to remove EXIF metadata before upload. Still verify the Worker upload authentication, file restrictions and deletion/retention policy.
- Choose and implement a retention/deletion period for reports, private locations, photos, phone details and push tokens. Expiring a report in the UI does not delete its Firestore document or image.
- Hosting headers protect transport/browser handling; Firebase platform encryption covers stored data; browser code cannot make database access controls unnecessary.

## Rollback

If V40 has a problem, redeploy the V39 hosting/rules snapshot. Do not restore older permissive rules without reviewing access to `reportLocations` and the user profile fields.
